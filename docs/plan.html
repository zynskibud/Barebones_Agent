Barebones Agent Grid

Project H1. One agent loop, tested across 162 configurations.

  • Agent = model + harness. The harness does not think. It sends messages to the model, runs the tools that the model asks for, and sends the results back.
  • The loop is the two return arrows. Tool results go back to the harness, and the harness sends them to the model. This repeats until the stop check ends the task.
  • The codebase is inside the environment. It is files on a machine. The shell, git, and the test runners act on those files.
  • Each colored chip is one axis in the Configurations tab. 3 × 3 × 3 × 3 × 1 × 2 = 162 configurations. The model is fixed. Thinking is on or off.
harness 3× tools 3× env 3× codebase 3× model 1× thinking 2= 162

The axes

Five independent axes. Pick one value on each axis. Each set of five picks is one configuration.

Configuration
Draft for review

An eval scores one whole configuration on a fixed task suite. No eval scores the model or any other axis by itself. To measure one axis, compare configurations that differ only on that axis.

One trial

A trial is one attempt at one task. The eval harness runs these steps for every trial.

  1. Make a clean copy of the task repo in the environment.
  2. Give the task prompt to the agent.
  3. Let the agent loop run until it stops, or until it hits a limit.
  4. Save the transcript: every message, tool call, and tool result.
  5. Copy the hidden tests into the repo and run them. Pass or fail.
  6. Record the result, tokens, turns, and time.
  7. Delete the environment.

Fixed parts

These parts are the eval harness. They stay the same for all 162 configurations. If one of them changes, old scores and new scores cannot be compared.

Questions and predictions

One question for each axis. Write the prediction before the run. Then the result can surprise you, and a surprise is where you learn.

AxisQuestionPrediction
ToolsWhich tool set solves the most tasks?The 3 file tools score lowest. They cannot run code, so the agent cannot run the tests to check its own work.
EnvironmentDoes the environment change the score?A small change in pass rate. A larger change in time and in infrastructure failures.
CodebaseDoes the language of the codebase change the score?Unknown. Rust has less training data, but its compiler gives the agent clear error messages.
HarnessDoes the harness language change the score?No change. If the scores differ, one harness has a bug. This axis is a correctness check.
ThinkingDoes thinking raise the pass rate? What does it cost in time and tokens?Thinking raises the pass rate on the harder tasks. It makes each trial much slower.

Decisions for you

Each item has my recommendation. Change any of them.

  1. How many tasks?Recommendation: 10 per language. Fewer tasks make the noise too large. More tasks cost more time to write.
  2. Write your own tasks, or use a public benchmark subset?Recommendation: write your own. Writing tasks and hidden tests teaches you what makes a task gradeable. A public subset is a good second check later.
  3. How many trials per task?Recommendation: 3 for stages 1 and 2. Raise it for any comparison where two scores are close.
  4. Which baseline?Recommendation: Python harness, file tools + bash, laptop, Python codebase, Qwen3 8B, thinking off. This is the H1 agent plus a bash tool, so the agent can run tests. Thinking off makes the pilot faster.
  5. Run stage 3?Recommendation: decide after the pilot. The pilot gives the real time per trial. Multiply it by 4,860 before you commit. At 5 minutes per trial, the full grid takes about 400 hours of machine time.

Public benchmarks, later

The 30 tasks in this repo are a small private suite. The goal after Experiment 1 and stage 2 is to run the same harness on public benchmarks, hit the published numbers for small models with harness engineering alone, and then try to beat them. The model stays Qwen3 8B. Only the harness changes.

OrderBenchmarkWhat it isWhy it is safeFirst run
1Terminal-Bench 2.1 (May 2026)89 terminal tasks in containers, run through Harbor. Versions 3.0 and 4.0 are rolling sets.Fixed and versioned. Released a year after the model's training data.A 20-task subset. Needs one Harbor adapter that starts the harness in task mode.
2SWE-bench Live (Microsoft, monthly)Real GitHub issues rebuilt into Docker environments each month. 743 multi-language tasks as of May 2026.Only issues filed after April 2025 are used.30 tasks from one monthly set.
3SWE-rebench (Nebius, monthly)Fresh issues each month, with a public leaderboard that lists open-weight models.Same rule: issues dated after the model's training data.30 tasks. Compare the number with the other small models on the board.
  • The contamination rule. Qwen3 8B was released in April 2025. A benchmark task counts only if it was created after that date.
  • The expected start. Fine-tuned 8B models built on Qwen3-8B reach about 40% on SWE-bench Verified with strong scaffolds and 64K to 128K context. A bare harness with a 32K window starts in the low single digits. That number is the baseline to beat, not a leaderboard entry.
  • The order of work. Experiment 1 first. If the prompt or thinking mode moves the private pass rate, the public runs use that setting. Then the Harbor adapter, then Terminal-Bench 2.1, then the two issue benchmarks.
  • The record. Every public run gets the same harness card as a private run: model digest, prompt version, tool set, env, limits, and the benchmark version, so the number can be reproduced.

Part 2 · next

Build waves

Every part gets built now, in waves of subagents. Two facts set the order.

  1. The Python harness is the reference. It settles the open points in the spec against real Ollama, and it defines the env interface. The TypeScript and Go ports copy a finished design, so they come last.
  2. Each agent owns one folder and never runs git. The main session commits at the end of each wave. Only one agent per wave edits the spec, the README, CLAUDE.md, and this page. Every other agent reports the changes it needs, and the next integration wave makes them.

The model rule

  • Fable 5.1 for work that needs judgment across the whole repo: the reference harness, the task design, and every integration wave. These agents decide things and debug across boundaries.
  • Opus 5.5 for work against a fixed contract: the eval harness, the two ports, the two envs, and the task ports. The spec and the Python reference tell them what correct looks like.
  • No Sonnet or Haiku. The cheap work in this project is too small to split off.
